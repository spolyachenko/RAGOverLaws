## 1. ГигаАгент (Фролов, 26 мин)

**Суть:** ГигаАгент вырос из open-source проекта **Ouroboros** (автор — Антон Рыжкаев, ИР АИ; «3 ночи, $3000 API»). Полгода назад принесли в команду ИИ-в-стройке; за полгода превратился в продукт. 17 000+ пользователей за полгода; доступен на GigaAgent.ru, Cloud.ru, Noura.ru (закрытые доступы) и GitHub (open-source).

**Архитектура:** от монолита до **трехслойной**: защищенное ядро / окружение-контракты / навыки-интерфейсы. Эволюция разбита на два уровня:
- эволюция самого агента (сложно, в прод не применимо),
- **эволюция навыков и интерфейсов** — «контролируемая эволюция», вот оно будущее.

**Что умеет сейчас:** единый долгосрочный контекст, 24/7 проактивность в фоне («напомнить о встрече» → сам подготовил материалы и пробрифил), управление телефоном, ROI-агенты для сложных задач, носимые устройства (Сбер-кольцо, Garmin, ВУП).

**Методология:** не мировые бенчмарки, а тестовые «корзины» из анонимизированных данных пользователей (внутренние + внешние). Пример: агент «решает» задачу про смету ремонта на бенче, но специалист видит невалидный результат — корзины ловят именно это. Платформа **GigaEvo** — среда, где агент сам себя улучшает (пока закрытый контур, результаты показывают).

**Q&A (существенное):**
- **Самобучение без RAG**: «у нас нет рагов». Собирают бизнесовые метрики + логи пользователей; пробуют варианты (упоминают «абляцию»). Эволюция агента происходит в изолированной среде на данных клиента.
- **Токен-экономика**: признают кратно больший расход, чем у стандартных harness. Решение — **режим nano (~80k токенов/цикл)** в OSS-версии; отключив self-evolution агент стоит как любой другой, но качество на многих задачах выше.
- **Интеграция в контур клиента**: open-source, разворачивается как обычный сервис, нужна только своя инференс-мощность. Скоро в OSS — многопользовательская версия (маленькая VM на отдел).
- **Почему свой, а не западный harness**: полный контроль/безопасность; «у западных по 200 патчей в день», нечем гарантировать целостность в закрытом контуре.
- **Философия**: «цифровой сотрудник» — не обучать агента, а как новому сотруднику объяснить словами один раз; поправки запоминаются в долгосрочную память (формат хранения — любой: файл/JSON/S3).

## 2. GigaCode как драйвер AI PDLC (Белоцерковский, 31 мин)

**Суть:** доклады «белой вороны» — он не разрабатывает GigaCode, а **приземляет его на ~2000 инженеров СберТеха** (DevEx). Стратегия: сейчас — «я выполняю, человек валидирует», дальше — полная автоматизация. GigaCode движется к **универсальному harness + специализациям по ролям** (аналитики, техписы, тесты).

**Компоненты:** AI Factory (модели), **policy engine в harness** (enterprise-ready — критично), MCP + agent skills **с корпоративным маркетплейсом** (шеринг наработок, чтобы не дублировать), plan-мод/сабагенты (классика).

**Поверхности:** IDE-плагины (VS Code, GigaIDE, JetBrains), **CLI** (демократизировался до не-инженеров — координатор работает в CLI), **Desktop** (спикер переехал с CLI на Desktop), GitVerse (агент GigaCode рядом с кодом).

**Почему корпоративный, а не OSS harness (аргументация):**
- **Supportability** — кто чинит, когда тул сбил в ситуации;
- **Updatability** — OSS-инструменты обновляются с «улучшили функциональность» без деталей, в корпорации это нельзя контролировать;
- **Reliability** — реакция бэка на большие нагрузки; пример: баг в апстриме с сентября — «никому не нужен, приоритет не поднять, коммент на GitHub — и забанят».
- Тренд: иметь «гигиенический минимум» своего — у них «среднемум/максимум».

**Q&A (существенное):**
- **Уведомления о конце работы агента** — признали боль (за пределами IDE используют «вайб-айланд»); совет: «заапдейтиться», либо **попросить GigaCode самому сделать уведомления — работает**.
- **Агентизация бюрократии**: разработчики убежали вперед и упираются в процессы (техпис, согласования). Кейс: агент для юристов проверяет сложные артефакты за 10 минут вместо 3 встреч с владельцем продукта. «Бюрократия останется навсегда — должен же быть блокер творчеству».
- **Контроль агентов в прод-среде** (DevOps): процесс **регистрации агентов** (архитектура, лимиты) — просто лимиты ломают процесс, а единая архитектура/best practice помогает.
- **Недетерминированность отпугивает**: «недетерминированность возникает из модели, а не из инструмента»; пример Qwen3.8 vs GLM на одной задаче (10 мин vs 1 мин); лечится настройкой harness (rules/системный промпт); полная детерминированность — специализированный harness.
- **DevX vs ProdX**: по DevX методики есть (20 лет), по ProdX «ничего нет, мы в предтече».

## 3. GigaStudio (Тельнов, 30 мин)

**Суть:** как сделать автономного агента **надежным** для конечного пользователя. Роль человека — творчество/гипотезы, агент — инженерия end-to-end (код, тесты, деплой, сопровождение) в циклах длиной часы-ночи. Три сущности: человек / платформа / агент.

**Архитектура (технически самое ценное):**
1. **Агентский мост** на протоколе **AG-UI** (открытый, SDK на разных языках) — мост добавляет перзистентность: каждое сообщение/обновление/намерение хранится «на бесконечность»; агент может заснуть ожидая ответа пользователя на день-неделю и продолжить «как будто не было».
2. **Durable execution** (платформа длительного исполнения, «как Temporal»): агент — не сервис, а **хранимая процедура/граф исполнения** (манифест или питоновский код с рантайм-решениями). Платформа владеет машиной состояния: падение субагента B → политика рестарта с последнего сохраненного действия, **выполненные действия не повторяются** (идемпотентность по эффектам); переживает падение целых нод.
3. **Обязательные этапы в цикле**: планирование, проверка результата, линтеры/валидация кода.
4. **Слой виртуализации** (Cloud.ru Container Apps): агент не знает про облако — только «файлики локально»; пользователь не видит облачные ресурсы.

**Киллер-фича**: **параллелизация** — агент сам решает, что задачи атомичны, и раскидывает по субагентам (демо: A и C завершены, B упал → авто-рестарт B → продолжение).

**Q&A:**
- Сайт из GigaStudio можно деплоить в прод (облако, сбор данных пользователей), но РФ-законодательство про ПДн — подпомогут; ИП/ОО не зарегистрируют.
- **Бенчи качества**: «измерять end-to-end сложно»; есть собственный пайплайн замеров (компилируется, тесты, качество продукта) — иначе «деградации качества вслепую».
- **Сравнение**: не с кодинг-агентами (Cursor/кодекс — фокус на код), а **с полностью автономными системами** (Devin-класс), соперничают с ними.
- **Проблема уникальных админок**: ИИ каждый раз генерит уникальный UI админки → нет специалистов по сопровождению. Решение в планах: **переиспользуемые облики/дизайн-критерии** (уже сейчас — файл с критериями приемки в промптах, дальше — универсальная система).
- Инференс: можно подключить внешние провайдеры (Foundation Models, Cloud.ru) — не только своя модель.

## 4. AI Studio (Жмакина, 24 мин)

**Суть:** не про агентов — **рабочие задачи за пределами чата** (ai-studio.giga.chat, пока все бесплатно). Прогон гипотетической задачи («добавить выгрузку отчетов в Excel») по инструментам:

- **Сравнение моделей**: две модели рядом, системная инструкция, температура, лимиты токенов, инструменты (поиск, интерпретатор); конфигурации сохраняются/экспортируются в JSON.
- **RAG-база знаний**: чанкинг/стратегия поиска настраиваются; ответы — «суммаризация ГигаЧатом + фрагменты с источниками», можно вернуться к фрагменту в документе.
- **Deep Research (Исследование)**: пайплайн с видимыми таймингами (критерии → поиск → оценка компетентности источников), black/white-листы ресурсов, фоновый режим, отчет с источниками; отчет можно загрузить обратно в RAG.
- **Meeting Companion** (десктоп): сам определяет начало встречи, **real-time транскрипция по ролям** (аудио не сохраняет), протокол/выжимка/задачи в трекер по окончании.
- Остальное: голосовая подготовка к выступлениям, TTS (паузы/интонации), распознавание аудио/лекций/подкастов с суммаризацией, GigaBlox (сборка своего агента).

**Q&A:**
- Внутри банка есть и «AI-студия Interno» с другим набором (NDA). Модели — **только GigaChat**, китайских аналогов нет.
- Meeting Companion: real-time транскрипция (ушел на 5 мин → вернулся в контекст), суммаризация пока только post-hoc.
- Галлюцинации: подбор промтов = «голый ГигаЧат» (может галлюцинировать без строгой системной инструкции); Deep Research — только по источникам.
- Конкурент по самооценке — **Google AI Studio**; метрика — возвращаемость (зарелизились недавно).
- Планы: **персональные API-ключи** на все сервисы, Kandinsky 3D, voice cloning, ноутбуки.

## 5. GitVerse: от ассистента к агентной фабрике (Шипов, 35 мин) — **самый плотный доклад**

**Суть:** агентная разработка = совместить два полюса: классический контролируемый CI/CD (медленный, десятки изменений/день) и «чемпионы» со 100x скоростью, чей опыт **не масштабируется** на команду (20/80, высокий порог входа).

**Три проблемы:** (1) опыт чемпионов не переносится; (2) **потеря контекста** — тысячи костылей в коде, без контекста агент «выпилит и сломает»; (3) парадигма «микроменеджмент локальных агентов» → надо к среде с тысячами агентов.

**Трансформация:** агенты — first-class citizens процесса; единица работы — **задача/intent**, весь контекст вокруг нее. Требования к IDP (GitVerse): масштабируемость (десятки тысяч параллельных агентов vs сотни CI-запусков), среды исполнения, управление контекстом/памятью на уровнях человек/проект/компания, **совместимость с OpenSpec** (SDD), быстрый старт, **постепенная** трансформация классического конвейера.

**Три режима взаимодействия:** human-interactive; **рутины по расписанию** (автопроверка оформления задач, релиз-ноты, сверка документации); **автономные агенты в производственном процессе**.

**Архитектура пайплайна:** конфигурация + задача + MCP-серверы + скиллы → среда исполнения → **harness (GigaCode CLI, но поддерживают любой — OSS/коммерческий)** → тулы/компиляторы → модель через **gateway с гардрейлами** → артефакты для людей и агентов. Можно строить цепочки: агент-аналитик → разработчик → тестировщик → ревьюеры.

**Цифры (важно):**
- Инфраструктурное потребление на запуск агентов vs CI/CD — **выросло на 2 порядка**.
- За прошлую неделю: **22 задачи (≈16%)** в релизе GitVerse решены агентами **полностью автономно** (пришли утром — приняли); проникновение инструмента в команде >90% без административных рычагов.
- **Метрика**: не строки кода, а «задачи, попавшие в релиз с коммиттером-агентом и ≤1 взаимодействием с человеком».

**Q&A (существенное):**
- **Человеческое ревью не должно быть бутылочным горлышком**: сначала автоматизируйте процесс (тесты, канарейки, AB-сверки) — «если проверяете 2-мя людьми, плохие новости, почините сначала». Вовлечение человека смещается в «сделали ли то, что нужно пользователю». Нагрузку агент может запустить и интерпретировать в своем окружении; для сверхнагруженных — изолированная канарейка.
- **Агентная идентичность** (agentic identity/personality): агенты сейчас работают через учетку пользователя; думают как про суб-идентити/делегирование полномочий, «на уровне стандартов, OIDC и всего остального». Решено: управление полномочиями на уровне GitVerse.
- **Почему 16%**: (1) агенту не хватает документированного контекста («не знает, что система работает без интернета»); (2) стоимость/объем инференса больших моделей → в системе появился **выбор моделей по типам задач** (тривиальное кодирование — на дешевые).
- **Экономика**: «эффект бесконечный — инференс ночью практически бесплатный» (свои GPU).
- **Кто отвечает за изменения агентов** (вопрос из ЦБ): законодательно — гендиректор/бухгалтер; фактически — **владелец процесса разработки**, а не «эфирная сущность».
- **Mobile-тесты** (T-Банк): Android-эмуляция зашита в дефолтные образы GitVerse; iOS — раннеры на маках, «надо пробовать».
- Визионерский финал: physical AI + перестройка ролей («в 2000-х была одна роль — разработчик-всем-на-свете»).

## 6. Evolution Foundation Models (Мазаев, 32 мин)

**Суть:** Cloud.ru, группа **FF Factory**. Foundation Models = **гейтвей к сотням моделей** («русский OpenRouter», но в РФ-контуре): OpenAI- и **Anthropic**-совместимый API, смена модели строкой в запросе, 7 форматов API (completions, Anthropic, embedder, reranker, STT, TTS, с вчера — Salute Speech real-time). 100+ моделей в каталоге (23 на своей инфраструктуре в РФ), 1,9 трлн токенов за 2026, 6225 постоянных пользователей.

**Архитектура** (свои, не из OSS — «в опенсорсе одни монолиты; LiteLLM деградирует при росте трафика»):
- **Control plane**: Model Manager (динамические конфиги), Users API, API Key Manager, User Stats, **Guardrails Manager**.
- **Data plane**: прокси на **Envoy + LLM-фильтр** (model name из тела запроса → хедер), **EPP** (endpoint picker), квоты/RPS/solvency-чекер, генеративный модуль для выхода за контур; все за Cloud.ru-сервисами (AMP, квоты, басы).
- Фазы обработки: request header/body/trailer, response header/body — «за десяток миллисекунд».

**Киллер-фичи:**
1. **Изоляция префиксного KV-кэша между арендаторами** — защита от KV-cache leakage (перетекание кэша одного пользователя к другому, боль для enterprise). Реализация: соль на кэш, «фича в самих движках (vLLM, SGLang) — просто правильно научились использовать».
2. **Guardrails-фильтр** (open-source: github cloud.ru / **LLMFilter**) — анонимизация PII/секретов на входе, подстановка оригиналов в ответ в том же чанке; open-source покрывает ~97% утечек секретов, enterprise-версия в контуре клиента — 98%. Fail-open + алертинг («ключи утекли — перевыпустите»).
3. **EPP-роутинг**: не round-robin (не работает из-за KVCache), а выбор пода по взвешенной сумме: **префикс-кэш, очередь, KV-занятость, z-score**.

**Инфраструктура:** свой GPU-парк (vLLM + SGLang), **автоскейлинг по комплексной нагрузке модели, а не по CPU**, все модели прогреты, NVFP4/FP4 модели → backfill-модели, в работе **передача моделей GPU→GPU минуя CPU** и **disaggregated-кластер** (prefill/decode раздельно, общий KVCache через KVBM-ноды).

**8 принципов:** порядок проверки = часть контракта; fail-open/close по риску; нет данных → не запрещено, есть гардрейлы; idempotency один раз; round-robin на горячем пути; ошибка конфига = несостоявшийся деплой; учет не мешает трафику; **инференс-движки не модифицируются** (PR/MR + конфигурации).

**Q&A:**
- **Новый под с пустым кэшем**: пока — распределенный кэш через S3, перегруженные поды остаются, новый прогревается; в disaggregated — общий KVCache.
- **SLA 99,9%**, георезервирование — «у нас все хорошо».
- **Цена выше OpenRouter**: 90% трафика днем, ночью железо стоит → ночной тариф (23:00–06:00 «практически по ценам OpenRouter»); планы: прямые контракты с азиатскими поставщиками, **low-speed/low-price модели** (первая цель — Qwen 27B).
- **Анонс: подписки** — формат Anthropic (тиры моделей и подписок, 5-часовые/недельные лимиты, extra usage), тот же API/SDK, pay-as-you-go остается.
- **Аудитория**: enterprise, «в enterprise лишь только одно — безопасность»; в планах — отечественный фильтр ГигаЧата на все модели.
- Напутствие: **под каждую задачу — правильную модель** («не надо Opus для "какая погода"»); будущее — автономные агенты в изолированных средах с контролем доступов; лично — voice-агенты («езжу в машине и обсуждаю с ГигаАгентом через Salute Speech свою же презентацию»).

## Кросс-паттерны трека (мои заметки)

1. **Все ушли от prompt-engineering к harness-инженерии** (GigaCode-доклад это прямо формулирует; GigaStudio — durable execution; GitVerse — среды исполнения).
2. **KV-cache — центральная боль инфраструктуры**: изоляция между арендаторами (Evolution FM), EPP по прогретости (Evolution FM), cache-aware routing (доклады на другом треке). Это ровно то, что мы крутим на 111/146/151.
