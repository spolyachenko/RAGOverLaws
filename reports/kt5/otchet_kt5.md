# КТ5. Генерация, оценка качества и продвинутый RAG

## 0. Отправная точка (КТ4) и фиксация конфигурации

- **Best retrieval (КТ4)**: HyDE + dense (bge-m3) + CE-реранк (bge-reranker-v2-m3, pool 20) — R@5 0.857.
- **Baseline retrieval (КТ3)**: dense bge-m3, Qdrant hnsw_m32_ef200 — R@5 0.768.
- Контекст для генерации: **top-5 чанков** (текст + заголовок) из каждой конфигурации, все 100 вопросов gold100.
- **Модель генерации и судьи**: Qwen/Qwen3.8-27B-FP8 (shared .239), temp=0, thinking off.
- Промпт генерации **зафиксирован** (не менялся в течение КТ5):
  > Отвечай ТОЛЬКО на основании предоставленного контекста. Если ответа в контексте нет — ответь ровно: «Не знаю». Не используй знания вне контекста. Отвечай сжато, 2–6 предложений, указывая источник (закон, статья), если он есть в контексте.

## 1. Генерация: baseline vs best (200 ответов)

| | faithfulness | relevance | utilization |
|---|---|---|---|
| baseline | 4.810 | **4.680** | 3.120 |
| best | **4.820** | 4.570 | 3.110 |

(среднее по 1–5 шкале, n=100 на каждую конфигурацию; полный разброс — data/kt5_judge_agg.json)

По типам (F / R / U):

| тип | baseline | best |
|---|---|---|
| factual (30) | 4.80 / 4.60 / 3.53 | 4.80 / 4.50 / 3.53 |
| composite (30) | 4.60 / 4.37 / 2.87 | 4.60 / 4.50 / 2.80 |
| abstract (20) | 4.95 / **4.95** / 3.00 | 5.00 / **4.35** / 3.05 |
| negative (20) | 5.00 / 5.00 / 3.00 | 5.00 / 5.00 / 3.00 |

**Главный результат: механизм «Не знаю» работает** (в КТ1 no-RAG было 0/100 отказов при явном
инструкте — модель галлюцинировала). Здесь, при контексте + той же инструкции:
negative-вопросы — **19/20 (baseline) и 20/20 (best) корректных отказов**, judge ставит
F=5, R=5.

Цена работы: у модели включается консервативный режим — **false-refusals** (отказ, хотя
информация была в контексте; по вердикту judge): baseline 3, best **6**. best отвечает
на 2 вопроса больше (50/80 против 48/80), но и отказывает на 3 лишних — эффекты
взвешиваются, и judge-баллы конфигураций практически равны.

**Вывод §1: преимущество лучшего ретрива (R@5 +0.09) на уровне генерации с top-5
контекстом не конвертируется** в качество ответа — генератор (27B + жёсткий инструкт
«Не знаю») становится bottleneck: он одинаково часто «дожимает» слабый контекст
baseline и одинаково часто отказывает на сильном контексте best.

Генерация: 1 442–1 450 prompt + 101–111 out токенов, med 1.6–1.7 с на ответ (shared .239).

## 2. LLM-as-a-judge

3 независимых критерия, каждый отдельным запросом (не общей оценкой):
**faithfulness** (только информация из контекста), **answer relevance** (отвечает ли
на вопрос), **context utilization** (использован ли релевантный контекст). Шкала 1–5
с якорями каждого балла прямо в промпте. Правила для «Не знаю» зашиты в промпты
(легитимный отказ: F=5, R=5, U=3; уклонение при наличии информации — низкие баллы).

### 2.1 Валидация промпта (обязательная)

30 пар (8 factual / 8 composite / 7 abstract / 7 negative × 2 конфига = 60
критерий-оценок), 2 прогона temp=0, точное совпадение балла (цель 85%+):

| критерий | v1 | v2 (финальный) |
|---|---|---|
| faithfulness | 58/60 = 96.7% | **60/60 = 100%** |
| relevance | 59/60 = 98.3% | **58/60 = 98.3%** |
| utilization | 55/60 = 91.7% | **58/60 = 98.3%** |

**Расхождения v1 (8, из ≥5 обязательных — разбор):**

1. utilization 3 vs 2, «вернуть телефон»: «использует фрагмент [1], игнорируя [2] и [4]» —
   судьи расходились, ключевой ли пропущенный фрагмент. В промпте было «значимые части
   проигнорированы» — «значимый» не определён. **Исправление (v2)**: явное правило —
   фрагмент КЛЮЧЕВОЙ, если без него ответ был бы другим (цифры/сроки/порядок),
   иначе НЕКЛЮЧЕВОЙ; 3 = пропущен неключевой, 2 = пропущен ключевой.
2. faithfulness 5 vs 3 на отказе: j1 применил правило «честный отказ → 5», j2 — основную
   шкалу и дал 3. **Исправление (v2)**: правило отказа вынесено в начало критерия и
   сделано императивным («обязательно применить первым шагом… оценки 1, 2, 4 на отказ
   не ставятся»).
3. utilization 3 vs 1 на отказе: судьи разошлись **фактически** — есть ли в контексте
   «15 дней для товара ненадлежащего качества» ответ на вопрос про исправный телефон.
   Это не баг шкалы, а граница семантической релевантности — v2 это не лечит
   (и не должно).
4. relevance 4 vs 3, «госпошлина за развод»: relevance-судья начал штрафовать за
   фактическую ошибку в ответе (это критерий faithfulness). **Исправление (v2)**:
   «фактологические ошибки НЕ снижают балл relevance».
5. utilization 4 vs 2, та же госпошлина: скачок на 2 балла при разной оценке
   «ошибочное объединение случаев». **Исправление (v2)**: то же правило ключевых
   фрагментов сужает вариативность.

Итерации зафиксированы: v1 (data/kt5_judge_val_v1.json) → разбор 8 расхождений →
v2 (data/kt5_judge_val.json). Остаток v2 — 4 расхождения, все ±1, из них 2 —
фактические споры о контексте (типа п.3), 2 — та же пограничная семантика.

## 3. Валидация человеком

Выборка **20 ответов** (10 вопросов × 2 конфига: 3 factual / 2 composite / 2 abstract /
3 negative) с полными контекстами — `data/kt5_human_sheet.md`, колонки F/R/U под
ручную оценку по тем же якорям. Weighted Cohen's Kappa по каждому критерию
(LLM-судья vs человек) считается после заполнения: κ>0.6 — надёжен, 0.4–0.6 —
условно, <0.4 — переработать промпт.

Статус: **лист готов, ручная оценка — за пользователем**; до её заполнения
надёжность судьи опирается только на валидацию «два прогона» (§2.1: 98–100%).

## 4. Выводы

1. **Инструкция «Не знаю» + контекст работают**: negative 19–20/20, judge F=R=5 на
   отказах. Конвейер RAG (ретriv → контекст → жёсткий инструкт) решил проблему
   бесшабашных ответов КТ1.
2. **Лучший ретрив не улучшает генерацию на этом датасете**: F/R/U baseline и best
   статистически равны (разницы ≤0.11 при n=100). При top-5 контексте генератор
   — bottleneck: он и «дожимает» слабый контекст, и консервативно отказывает на
   сильном.
3. **Цены лучшей конфигурации**: false-refusals 6 против 3 (abstract-вопросы
   страдают: R 4.35 против 4.95) — HyDE-топ-5 уже «уходит» в соседние статьи,
   и модели проще отказаться, чем отвечать по обрывкам.
4. Рекомендации на прод/дальнейшие итерации: (а) смягчить инструкт отказа
   («отвечай, если в контексте есть хотя бы релевантная норма; «Не знаю» — только
   если нормы нет вовсе»); (б) расширить контекст до top-10 (у best R@10 = 0.893);
   (в) для abstract-вопросов — отдельный промпт (разрешить обобщение по контексту).
   Любое из трёх проверяется повторным прогоном КТ5 (промпт уже не фиксирован).
5. Продвинутый RAG (граф/агент) — опциональная часть ТЗ, не реализован: на
   текущем корпусе (статьи законов, вопросы локальные) его выигрыш неочевиден,
   а стоимость построения графа/агента несоразмерна задаче.
